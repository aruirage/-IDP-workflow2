# AI自動生成：分批生成设计说明

> 对象：帳票タイプ設定 Step2「読取項目設定」的 `AI自動生成` 按钮
> 目的：解决一次性生成全部字段的 提示词 / 正确样例 时超出模型 token 上限的问题

---

## 1. 背景与问题

`AI自動生成` 现在是一次请求，为**全部字段/列**生成 プロンプト（提示词）与 正解サンプル（正确样例）。

字段数量一多，请求就会超过模型的 token 上限，表现有三种：

- 返回的 JSON 被截断，只有前半部分字段拿到结果；
- 末尾若干字段为空；
- 整条请求直接报错，所有字段都拿不到结果。

## 2. 根因

超限发生在**输出侧**，不是输入侧。

- **输出** = N ×（提示词 + 正确样例）。按每字段 80～150 token 估算，100 个字段就是 1 万 token 以上，超出很多模型的单次输出上限。
- **输入**：样张图像是固定成本（一张 A4 扫描图约 1.5k～3k token），**不随字段数增长**；全局背景输入上限 2000 字。两者都不是瓶颈。

结论：切分维度必须是**字段**，不是图片。

## 3. 方案：两阶段 + 按字段分片

```
输入（全局背景 + 样张 + 全字段定义）
  │
  ├─ ① 全体解析（只跑一次）
  │      样张 + 全局背景 → 版面解读备忘（短文本）
  │
  ├─ ② 按字段分片，每片独立请求
  │      片 1：全局背景 + 解读备忘 + 字段 1–10   → 只返回这 10 个字段的结果
  │      片 2：全局背景 + 解读备忘 + 字段 11–20  → 同上
  │      片 3：全局背景 + 解读备忘 + 字段 21–30  → 同上
  │
  ├─ ③ 按字段 ID 合并，写回表格（按完成顺序逐行填入）
  │
  └─ ④ 失败的片二分割后重试，已成功的片保留
```

### ① 全体解析（只做一次）

用样张 + 全局背景，输出一段较短的「版面解读备忘」：账票有哪些区块、单位与格式约定、各字段大致位置。输出量小，不会超限。

### ② 按字段分片

每片请求携带：全局背景 + 版面解读备忘 + 本片字段定义（項目名 / タイプ）。只要求模型返回本片的 提示词 + 正确样例。

### ③ 合并

以**字段 ID** 为键合并回表格。

### ④ 重试

失败的片二分割后重试；已经成功的片不重跑。

## 4. 为什么先做 ①

- 样张只理解一次，后续每片复用同一份解读备忘，单位和格式约定不会各片写得不一样。
- 每片上下文被压到「2000 字背景 + 几百字解读备忘 + 十几个字段名」，输出也锁在 N 个字段以内。

## 5. 关于「模型没有跨批记忆」

**结论：不需要模型有记忆。** 分批的边界不由图片决定，由**字段清单**决定；跨批状态由后端持有，不放进模型上下文。

### 5.1 状态在哪里

后端维护一张 `field_id → { prompt, sample }` 的映射表：

- 每批请求**自带本批的字段清单**（含 field_id），模型不需要知道前面生成过什么；
- 响应**按 field_id 回填**，后端把结果写进映射表；
- 全部批次跑完后，后端算一次差集，缺失的 field_id 进下一轮重试。

模型「记不记得」不影响正确性——它每一批都只被要求处理明确列出的那几个字段。

### 5.2 真正需要处理的三件事

**（a）跨批写法不一致**

同一张票里，单位、日期格式、カタカナ / 漢字 之类的约定必须一致。做法：① 全体解析产出一份**约定备忘**（单位、格式、字段与区块的对应关系），之后**每批逐字重复**这份备忘。

不要把「上一批的输出」当作下一批的上下文——那样某批一失败，后面全崩。

**（b）同一张图重复理解，结果可能抖动**

视觉模型对同一张图多次读取，结果不保证逐字一致。做法：

- 降低 temperature（生成类任务用 0 或接近 0）；
- 或采用 5.3 的方案 B，让图片只被理解一次。

**（c）同一张图重复计费**

图片 token 每批都会算一次。做法：使用模型的 prompt / context caching，把「全局背景 + 样张」放在提示前缀，后续批次命中缓存。

### 5.3 三种做法对比

| | A. 无状态分片 + 前缀缓存 | B. 图片一次性转结构化文本（推荐） | C. 单会话多轮 tool-call |
| --- | --- | --- | --- |
| 图片传几次 | 每批都传（命中缓存后按缓存价计费） | **只传 1 次** | 只传 1 次 |
| 模型需要跨批记忆吗 | 不需要 | 不需要 | 有（同一对话） |
| 上下文增长 | 每批固定 | 每批固定 | 随轮次累积 |
| 成本可预测性 | 高 | **最高** | 低 |
| 主要风险 | 缓存未命中时成本翻倍 | ① 的解析质量决定上限 | 长对话漂移、时延不可控 |
| 适用 | 字段数中等、想最小改动 | 字段数大（100+） | 字段数少（< 50） |

**方案 B 的做法**：① 全体解析这一步不要只输出摘要，而要输出**逐区块的结构化全文**——每个区块的原文文本，以及该区块内有哪些字段。之后每一批只传「全局背景 + 这份结构化文本 + 本批字段定义」，**完全不传图片**。

- 好处：图片只花一次钱；所有批次看到的是同一份确定性文本，不存在抖动；上下文小、可缓存、可复现。
- 前提：① 的解析必须覆盖全部区块。所以 ① 要输出「全文」而不是「摘要」——漏掉的区块后面补不回来。

### 5.4 如果确实想让模型知道「哪些已完成」

在提示里附一份**已完成 field_id 的清单**就够了，不需要附结果内容。但这只是辅助手段：真正的一致性保障是 5.1 的差集校验和 5.2(a) 的共享约定备忘。

### 5.5 现有接口是单次无状态调用 —— 模型侧零改动

现在的实现是**一次交互**：把「一张图 + 全部字段」喂给模型，模型返回全部的 提示词 + 正确样例。这一次调用本身**不携带任何状态**，模型不保留上下文。

因此改成分批，**不需要动模型侧的任何东西**：

```
现在（1 次）
  POST /generate { image, global_context, fields: [f1 … f500] }
  → { results: [f1 … f500] }        ← 输出超限

改成（N 次，同一个接口、同一张图）
  for chunk in chunks(fields, 15):
      POST /generate { image, global_context, layout_memo, fields: chunk }
      → { results: chunk }          ← 每次只输出 15 个字段
  按 field_id 合并 + 差集重试
```

- 接口签名、请求格式、模型侧实现**完全不变**，只是 `fields` 数组变短、调用次数变多。
- 不需要多轮会话，也不需要模型「记住上一批」——单次调用里本来就不存在「上一批」。
- 新增的逻辑**全部在调用方（后端）**：① 切片 → ② 循环调用 → ③ 按 field_id 回填并算差集重试。

**需要确认的一点**：如果当前实现是把**已有的提示词 / 正确样例当作输入**喂回去（few-shot 示例），那么分批时每一批只能携带**与本批字段相关的**示例，否则上下文依然会超限。如果它们只是输出，则不涉及这个问题。

## 6. 参数建议

| 项 | 建议 |
| --- | --- |
| 分片大小 | 按输出预算反推：`N = floor(T × 0.6 / c)`，T = 模型单次输出上限，c = 每字段平均 token。经验值 **10～20 个字段/片** |
| 并发 | 2～4 个 in flight。串行最稳、最可预测；并行更快，但要注意限流 |
| 上下文缓存 | 把「全局背景 + 样张（或 ① 的结构化文本）」放在提示前缀，后续片命中缓存 |
| 幂等 | 默认只填空单元格；只有点「再生成」才覆盖。重试时先算差集，只补缺失字段 |
| 进度 | 按钮旁显示「已完成 / 总数」，行内保留「AI分析中…」占位；允许中途取消，已完成的分片结果保留 |
| 兜底 | 单片仍失败 → 二分割；切到 1 个字段仍失败 → 该行标红 + 单独的「再生成」入口 |

## 7. 接口契约（建议）

**请求（单片）**

```json
{
  "document_image": "<样张；方案 B 下可省略>",
  "document_text": "<① 产出的逐区块结构化全文；方案 B 使用>",
  "global_context": "<全局背景，≤2000 字>",
  "layout_memo": "<① 产出的约定备忘>",
  "fields": [
    { "field_id": "f_001", "name": "氏名", "type": "string" },
    { "field_id": "f_002", "name": "性別", "type": "string" }
  ]
}
```

**响应（单片）**

```json
{
  "results": [
    { "field_id": "f_001", "prompt": "カタカナで記載", "sample": "マエダ モヤ" },
    { "field_id": "f_002", "prompt": "○または✓が付いている方を選択", "sample": "女" }
  ]
}
```

要点：响应必须**只包含本片请求的 field_id**；缺失项由调用方判定并重试。

## 8. 注意事项

- **合并键必须是字段 ID**，不能用 項目名 —— 重名和改名都会打乱映射。
- **每片都要逐字重复全局背景和约定备忘**，不要用链式上下文。
- 表格 tab（テーブル情報読取）的列可以复用同一套逻辑，只把片键换成列 ID。
- 字段数上限越高越必须分批。

## 9. 验收要点

- 50 / 200 / 500 字段三种规模下都能完整生成，无截断、无空行。
- 中途取消后，已完成的分片结果保留，未完成的为空。
- 人为让某一片失败，重试后只有该片重跑，其他片结果不变。
- 重试到 1 个字段仍失败时，该行有明确的失败标识和单独的再生成入口。
- 跨批一致性：同一份生成结果里，单位与日期格式在全部字段上保持一致。
