# 三期 QR 字段归一方案（最小版 + 完整设计）

## 0. 最小方案（先看这一页）

先做第一步。第二步等客户定了字段表再做。全程不用大模型，卡住了再用。

### 第一步 · 把 QR 变成一份干净的字段列表（现在就能做）

不依赖客户，不调模型，纯规则。

| 动作 | 做什么 |
| --- | --- |
| 切分 | 按 `$` 切开；连续空值区归成一段；靠值的样子（数字 / 日期 / 一串 0 和 1）分段。不看字段名 |
| 归一 | 日期碎片拼起来（`2026` `5` `18` → `2026/05/18`）、年号换西历（`昭和` `42`）、全角转半角、去空格、`!s` 还原 |
| 画勾 | 一串 0/1 里取那个 1，变成一个字段（`0 0 1 0 0` → `継続`） |
| 剔除 | 帐票码、枝番这类系统字段扔掉 |

产出：`{ 字段名, 值 }` 列表，格式统一。407 个原始片段 → 约 40-60 个字段。

顺带的好处：这份列表直接就是给客户的 OCR 字段表提案。客户不知道该怎么配字段，是因为手上没有候选清单。

### 第二步 · 和 OCR 字段表对一遍（等客户定了再做）

| 情况 | 怎么处理 |
| --- | --- |
| 名字像 | 直接对上 |
| 名字不像，但值一样 / 是同一类（`2026` vs `2026/05/18`） | 也判对上 |
| 对不上 | 这个字段走 OCR |
| 名字不像、值也看不出关系 | 这一步才交给大模型 |

### 大模型用在哪

只在第二步最后一格 —— 名字和值域都判不出来的那些。先不用，卡住了再用。

---

以下是完整设计，当前阶段不必细读。

## 1. 二期的问题到底是什么

二期把 QR 与 OCR 当成两条**各自维护字段**的独立链路：

- QR 侧：`FIXED_DOC_QR_FIELD_NAMES`（A01 当前 407 项），按拼接后的 token index 逐位映射。
- OCR 侧：账票类型 Step2 的字段表（項目名 / タイプ / HITL / 必须 / プロンプト / 正解サンプル / 処理ルール）。

两边要靠人工保持一一对应。由此产生三个具体病症：

1. **两套字段表**。改一个模版要同时改 QR 字段名表和 OCR 字段表；字段增删后判定分母漂移（`qr-read-edge-cases.md` #21）。
2. **后处理靠字段名硬编码**。`main.js` 现在用 `/傷病|診断名|ICD10|医療機関/` 正则推断 `マスタ照合`，另有一张按字段名的固定映射表。每来一个新模版就要加规则，无法规模化。
3. **对齐失败代价是整份**。一个 token 对不上，406 个正确值全部作废，整份退回 OCR（全有或全无）。

三期的目标不是"再写一套更聪明的映射表"，而是**取消 QR 侧字段表这一层**：OCR 字段表成为唯一主数据，QR 只是数据源，两者之间的落差由一个可生成、可审核、可复用的**对齐计划**来承担。

## 2. 设计原则

| 原则 | 含义 | 解决什么 |
| --- | --- | --- |
| 单一主数据 | 只有 OCR 字段表是业务真相；QR 不维护字段语义 | 两套字段 |
| 模型在配置期，不在运行期 | LLM 只在生成/修订对齐计划时调用；运行时是纯确定性执行 | 成本、延迟、可复现、可审计 |
| 模版差异是数据，不是代码 | 新增模版 = 导入规格 + 生成计划，零代码改动 | 逐模版硬编码 |
| 锚点是多信号，字段名只是其中一票 | 位置结构 + 值域 + 样本一致性 + 类型相容 + 分组，字段名可选 | 不依赖字段名匹配 |
| 不确定就不猜 | 拿不准的条目落 `unresolved`，该字段走 OCR | 静默写错值 |

## 3. 整体架构

四层，其中第二层是三期新增。

```
┌─ 抽取层（已有）──────────────────────────────────────┐
│  OCR 路径：字段表 → OCR 抽出 → { fieldId: value }     │
│  QR  路径：扫描 → join('') → split(/[$^]/) → 原始序列  │
└──────────────────────────────────────────────────────┘
                        ↓
┌─ 对齐层（三期新增 · 配置期 · 调 LLM）─────────────────┐
│  输入：QR 字段集 + OCR 字段集 + 规则目录 + 模版画像    │
│  输出：对齐计划 AlignmentPlan（纯数据，版本化落库）    │
└──────────────────────────────────────────────────────┘
                        ↓
┌─ 执行层（运行期 · 确定性 · 零模型调用）───────────────┐
│  按计划逐条取源值 → 转换/合并/挑选 → 写目标字段        │
│  计划未覆盖 / 执行冲突 → 该字段落 OCR                 │
└──────────────────────────────────────────────────────┘
                        ↓
┌─ 校验层 ────────────────────────────────────────────┐
│  值域相容、类型相容、必需字段覆盖率；失败 → 整份 OCR   │
└──────────────────────────────────────────────────────┘
```

关键决策：**LLM 只在配置期跑一次（每个模版一次），运行期零调用**。把不确定性收敛到一次可人工审核的动作上，换来运行期的可复现与可回归测试。这是本方案与"每份单据让模型对一遍"的根本区别。

## 4. 输入定义

### 4.1 QR 字段集 `QrFieldSet`

来自 QR 规范 + 样张解码，**不含业务语义**。

```jsonc
{
  "templateId": "LIAJ045-A01-202104",
  "qrCount": 6,
  "tokenCount": 406,
  "fields": [
    {
      "index": 0,
      "hint": "帳票コード",        // 可选。规范里有就带，没有就 null
      "samples": ["040c1", "040c2"],  // 多份样张的去重样本
      "emptyRatio": 0.0,           // 样张间为空的比例
      "shape": "code"              // 由样本推断的形态，非规范给定
    },
    { "index": 2, "hint": "テンプレートID^患者氏名", "samples": ["LIAJ045-A01-202104^安達　珠美"], "subSplit": "^" }
  ]
}
```

`hint` 必须允许为空。方案在**没有字段名**时也要能工作 —— 这是通用性的分水岭。

### 4.2 OCR 字段集 `OcrFieldSet`（主数据）

即账票类型 Step2 字段表，加上值域画像。

```jsonc
{
  "docTypeId": "liaj-diagnosis",
  "fields": [
    {
      "fieldId": "f_001",
      "name": "患者氏名",
      "type": "string",
      "required": true,
      "hitl": true,
      "group": "患者情報",
      "samples": ["安達　珠美", "藤島 紗織"],   // 正解サンプル
      "rules": ["全角変換"],                    // admin 已配的 処理ルール
      "normalRange": null,
      "valueDomain": { "shape": "text", "pattern": null }
    }
  ]
}
```

### 4.3 规则目录 `RuleCatalog`

用户所说的"相应规则说明"，指两组目录。

**（a）既有的 15 个 処理ルール**（`main.js` `fixedDocProcessRuleOptions`）：
`マスタ照合 / 数字のみ / 小数点付きの数字 / カタカナ / ひらがな / 日付 / 金額（JPY）/ 金額（USD）/ スペース削除 / 全角変換 / 半角変換 / 半角変換（数字）/ テキスト置換 / バーコード / QRコード`

每个规则附：适用类型、输入输出形态、是否可逆、是否允许在 QR 路径使用。模型只能从这个目录里选，不能自创规则。

**（b）三期新增的对齐动作目录 `AlignmentAction`**（见 §5.2）。

### 4.4 模版画像 `TemplateProfile`（可选，但强烈建议）

给模型的结构性先验，全部来自数据而非代码：

- 字段分组（患者情報 / 傷病 / 手術 / 転帰 …）
- 值域字典 `ValueDomainDictionary`：按 `fieldId` 聚合枚举集合，来源 = 正解样本 + 历史抽出结果聚类。例：`転帰 → {治ゆ, 軽快, 継続, 中止, 死亡}`、`性別 → {男, 女}`、`年号 → {昭和, 平成, 令和}`
- 业务场景标签（診断書 / 保険金請求）
- 同 docType 下已存在的其他模版计划（供继承）

## 5. 输出定义：对齐计划 `AlignmentPlan`

### 5.1 Schema

```jsonc
{
  "planVersion": 3,
  "docTypeId": "liaj-diagnosis",
  "templateId": "LIAJ045-A01-202104",
  "basePlan": null,                 // 继承自哪个模版的计划（A04 可继承 A01）
  "routingMode": "field_level",     // field_level | all_or_nothing
  "entries": [ /* 见 5.2 */ ],
  "unmappedQr": [120, 121, 122],    // 明确剔除的 QR 位置
  "uncoveredOcr": ["f_410"],        // 计划未覆盖、运行时必走 OCR 的字段
  "summary": { "direct": 210, "merge": 12, "flagGroups": 9, "drop": 170, "unresolved": 6 }
}
```

### 5.2 动作目录（有限、可枚举，与字段名无关）

| action | 语义 | 典型触发 |
| --- | --- | --- |
| `direct` | 1 个 QR 单元 → 1 个 OCR 字段，仅做规则转换 | 值形态一致 |
| `merge` | n 个 QR 单元 → 1 个 OCR 字段 | 日期 年/月/日 三 token 合成一个日期字段；`昭和$42` 合成和历 |
| `split` | 1 个 QR 单元 → n 个 OCR 字段 | 一个 token 内含完整日期，OCR 拆成年/月/日三字段 |
| `pick_by_flag` | 互斥指示位组 → 1 个 OCR 字段（单选） | 転帰：5 位恰一个为 1 |
| `collect_flags` | 指示位组 → 1 个 OCR 字段（多选，按分隔符拼接） | 合併症可多勾 |
| `lookup` | 值 → 名称，走字典 | ICD10 代码 → 傷病名；区分番号 → 手術名 |
| `constant` | 固定值 → 字段 | docType 固定输出 |
| `drop` | QR 单元剔除，不写任何字段 | 业务不需要的字段 |
| `unresolved` | 不猜，该字段运行时走 OCR | 候选多义 |

## 6. 模型判断逻辑

不是"把两个列表丢给模型让它自由映射"，而是**确定性预处理 + 模型做选择题 + 确定性约束求解**三段。

### 阶段 0 · 归一化与画像（纯代码）

- QR 侧：`join('') → split(/[$^]/)`，逐 index 汇总多样张样本、空值率、形态（数字/日期片段/枚举/内码/自由文本）。
- OCR 侧：字段表 + 正解样本 + 类型 + 已配规则 + 值域字典。
- 建 `ValueDomainDictionary`：对每个 `fieldId` 聚合枚举集合与形态。
- **结构性剔除先做掉**：头部系统区（帐票码 `040c1`、枝番 `001`、`^` 两侧的 templateId 与已识别的患者氏名之外的字段）由确定性规则标 `drop`，不进模型。把模型工作量砍掉一大块。

### 阶段 1 · 结构切分（关键，决定规模化能力）

把 406 个孤立 token 切成 **30～60 个候选单元**。依据全部来自结构，不看字段名：

| 信号 | 判定 |
| --- | --- |
| 连续空值区 `$$$$…` | 天然段边界（LIAJ 大量连续空值） |
| 相邻 token 在样张间**互斥为 0/1** | flag group 候选（单选或多选由"是否出现过多个 1"区分） |
| 相邻 2～3 token 形态为 年/月/日 或 年号/年 | 日期组合候选 |
| 形态与邻近突变（数字 → 自由文本 → 数字） | 段边界 |
| `^` 子分隔 | 单元内部分裂 |

这一步把模型要判断的对象数量降一个数量级，是"适配大量模版"的成本前提。

### 阶段 2 · 候选对齐（LLM，分批）

对每个候选单元，模型在**受约束的候选集**里选目标：

- **输入**：候选单元（位置、多样张样本、形态、结构标签）+ OCR 候选集（名称、类型、正解样本、值域、分组、已配规则）+ 动作目录 + 约束（值域必须相容、类型必须相容、一个 OCR 字段最多被一个单元命中，除 `merge`）。
- **输出**：`{ targetFieldId, action, sources, transform, confidence, evidence }`，或 `drop` / `unresolved`。
- **硬约束**：只能从给定候选里选，不得自创字段或规则；每条必须给 `evidence`（引用样本、位置或值域事实），无证据不给映射。
- **参数**：temperature 0；按 docType + templateId 缓存，同输入必得同计划。

把"生成映射"降级成"做选择题 + 引用证据"，是为了让输出可被程序化校验 —— 这是通用方案能落地的必要条件。

### 阶段 3 · 约束求解与复核（确定性 + 第二遍 LLM）

- 硬校验：值域相容、类型相容、目标唯一、flag group 恰一个为 1（或全 0）、`merge` 的字段序合理。
- 冲突 / 多义 → 第二遍 LLM，**只带候选集**做裁决。
- 仍不确定 → `unresolved`，运行时该字段走 OCR。**绝不用低置信结果直接写值。**
- 覆盖率复核：`unmappedQr` 中是否藏着 OCR 侧 `required=true` 的字段；`uncoveredOcr` 是否为空。

### 阶段 4 · 人工审核与回流

配置端以表格展示计划：`QR 位置 | 样本值 | → OCR 字段 | 动作 | 置信度 | 证据`。低置信与 `unresolved` 高亮，admin 一键确认或改写。审核结果作为 few-shot 回流下一轮生成。

## 7. 处理流程

### 配置期（每模版一次）

```
导入模版（QR 规范 + 样张 / OCR 字段表）
  → 阶段0 归一化 + 值域字典 + 结构性剔除
  → 阶段1 结构切分（406 token → ~50 候选单元）
  → 阶段2 LLM 分批对齐
  → 阶段3 约束求解 + 复核
  → 阶段4 admin 审核确认
  → 落库：对齐计划成为账票类型版本的一部分
```

### 运行期（每份单据）

```
OCR 抽出 → ocrValues
QR 扫描 → join → split → qrValues（原始）
  ↓ 若 QR 可用
执行对齐计划：
  direct / merge / split / lookup / constant → 取源值 → 转换 → 写目标字段
  pick_by_flag → 扫组内 token，取 1 的那个 → 输出对应 label
  collect_flags → 收集所有 1 → 按分隔符拼接
  drop → 忽略
  unresolved / 执行冲突 / 值域校验失败 → 该字段标记为 OCR 来源
  ↓
合并结果 → 完整字段值集
  ↓
Step3 処理ルール → 正常条件 → HITL 判定（与二期一致）
  ↓
Step5 / 确认页按字段展示来源标签（QR読取 / OCR読取）
```

**与二期的实质差别：路由粒度从"整份"改为"字段级"。** 二期一个 token 对不上就整份退回 OCR；三期只有真正失败的字段退回，其余字段照常走 QR。安全网保留：必需字段覆盖率低于阈值（如 <80%）时整份退回 OCR。

**空值语义沿用二期**：QR 解码后为空 = 有效空值，不触发 OCR 兜底。

## 8. 三种情形的具体解法

### 8.1 多模版、每模版后处理字段不同

避免硬编码的三层手法：

1. **OCR 字段表按 docType 收敛，不按模版。** A01 / A04 / K01 同属 `liaj-diagnosis`，字段表是"LIAJ 診断書字段全集"，模版只决定"哪些字段出现"。模版差异全部下沉到对齐计划里，OCR 侧只有一套字段表。
2. **后处理规则挂在业务字段上，与数据来源无关。** 字段表已配 `処理ルール` 的，QR 写值直接沿用，模型不介入。只有字段表未配的，才由模型从"值域 + 类型 + 正解样本"推断（如样本恒为 `YYYY/MM/DD` → `日付`），且只在能推断时给建议，否则留空走 OCR。规则配一次覆盖该 docType 下全部模版。
3. **计划继承 + 增量。** 新模版可指定 `basePlan`（A04 继承 A01），只对差异部分重新对齐。LIAJ A01/A04 字段布局共享约 24%，继承能显著降本降错。

净效果：新增模版 = 导入 QR 规范 + 跑一次生成 + 审核，**零代码改动**。现状的 `/傷病|診断名|ICD10|医療機関/` 正则与按字段名的固定映射表可以整表删除。

### 8.2 QR 有、OCR 没有的字段如何剔除

判断信号（不靠字段名）：

| 信号 | 判定 |
| --- | --- |
| 目标侧不存在 | OCR 字段集中无任何值域/类型相容候选 → `drop` |
| 恒为常量 | 多样张里值不变（帐票码、枝番、机构内码）→ 元数据，非业务字段 → `drop` |
| 头部系统区 | 落在 `040c1$001$` 等结构头部 → 确定性规则直接剔除，不问模型 |
| 管理用内码 | 值为 `8036ｲ` / `サ` / 无对应语义的 `1`、`0` → `drop` |
| 冗余 | 同一 OCR 字段已被更高置信单元命中，本单元是其重复表达 → `drop` |

保守原则：**`drop` 只对"明确无目标"的单元做**。只要存在它是必需业务字段的可能，一律落 `unresolved` 走 OCR，绝不静默丢数据。每条 `drop` 必须落 `reason`，配置端可查、可一键恢复为 OCR。

### 8.3 打勾画圈类字段（QR 多字段 → OCR 单字段）

识别 → 配对 → 执行三步：

**识别**（怎么知道 394-398 是一组）
- 样本证据：这组相邻 token 在多样张中**恒为恰一个 1、其余 0**，或全 0（未选）
- 位置证据：相邻、等距、长度一致
- 对照证据：OCR 侧某字段的值域恰好覆盖这组选项的语义空间

**配对**（label 从哪来，按优先级降级）
1. QR 规范自带字段名 → 剥掉序号前缀得 label
2. OCR 侧该字段的值域字典与选项数一致 → 按样本命中关系配对（哪个 index 在样张里为 1，就对上该样张 OCR 抽出的那个值）
3. 模型基于选项序号 + 业务常识 + 值域推断，`labelSource: "inferred"`
4. 无法确定 label → `labelSource: "index_order"`，运行时输出序号，或该字段走 OCR

**执行**
- 单选（`pick_by_flag`）：取值为 1 的位 → 输出其 label；全 0 → 按 `emptyPolicy` 输出空；多个为 1 → 冲突 → 该字段走 OCR + 告警
- 多选（`collect_flags`）：收集所有为 1 的 label，按约定分隔符拼接或输出多值列表。单选/多选由样张统计判定（是否出现过多个 1）

同一套机制顺带覆盖其他"结构不一致"类型：日期碎片合并、年号合并、姓名分列、地址碎片、代码→名称（`lookup`）。**通用性来自动作目录有限且与字段名无关**，而不是来自对某个模版的定制。

## 9. 提升通用性与可扩展性的设计思路

| # | 思路 | 收益 |
| --- | --- | --- |
| 1 | 单一主数据（OCR 字段表） | 字段增删只改一处；分母不再漂移 |
| 2 | LLM 在配置期、运行期确定性执行 | 可审计、可复现、零运行延迟、成本按模版分摊 |
| 3 | 动作目录化（9 个动作） | 扩展 = 加数据或加一个动作，不是加一个 `if` |
| 4 | 锚点从字段名升级为多信号 | 无字段名的模版也能对齐；字段名只作加分 |
| 5 | 值域字典作为跨模版共享资产 | 字典越大对齐越准；可从历史抽出结果自举增长 |
| 6 | 计划可缓存、版本化、可继承 | 新模版从已有计划增量修正，不必从零 |
| 7 | 人工审核回流为 few-shot | 模版库越用越准，形成组织资产 |
| 8 | 三级降级链（字段级 → 整份 → OCR） | 永不静默写错值 |
| 9 | 计划是纯数据，可离线回归 | 拿历史样张比对 QR 路径与 OCR 路径的字段级差异，差异即回归用例 |
| 10 | 字段名遮蔽测试 | 把 QR 侧字段名全去掉重跑，看计划质量跌幅，作为通用性的量化验收指标 |

## 10. 风险与边界

| 风险 | 对策 |
| --- | --- |
| 模型幻觉、自由映射 | 只做选择题；必须引用证据；程序化约束校验；未决项不猜 |
| 样本不足（全空值、样张只有 1 份） | 置信度低 → `unresolved` → OCR。不硬猜 |
| 互斥位误判（恰一个 1 但实为独立字段） | 要求多样张一致 + 与 OCR 值域互证；单样张不足以判定 |
| label 配对错误 | 优先用样本命中关系而非位置顺序；无法确定则输出序号或走 OCR |
| 运行期成本 | 零模型调用；计划本地执行 |
| 新模版但 OCR 字段表缺失 | 先跑 OCR 抽出 → 用结果反向补字段表 → 再跑对齐 |
| 多账票类型互相污染 | 值域字典与计划均按 docType 隔离 |

## 11. 与二期现状的衔接

- `FIXED_DOC_QR_FIELD_NAMES` 从"业务字段表"降级为"QR 侧位置索引"，不再与 OCR 字段一一对应。
- `main.js` 的字段名正则推断（`/傷病|診断名|ICD10|医療機関/`）与按字段名的固定规则映射表删除，改由对齐计划承载。
- `fixedDocTestReadMode` 的判定从"整份值数相等"改为"字段级来源标记 + 必需字段覆盖率阈值"。
- `qr-read-edge-cases.md` 的 #11（相抵错位伪合格）在字段级对齐下自然缓解：每个目标字段由计划指定源位置，中段错位不再无声通过。

## 12. 多模版能否共用字段

结论：**能，而且必须共用**。但前提是先分清"共用什么"和"不能共用什么"——把模版差异一刀切地塞进共用字段表，会踩到三个坑（见 12.7）。

### 12.1 分层：字段字典 / 模版视图 / 对齐计划

三层的职责严格分开，"模版"这个概念被压缩到只剩第二、三层。

```
业务字段字典 BusinessFieldDictionary     ← docType 级，全模版唯一，配一次
        ↓ 子集 + 覆写
模版视图 TemplateFieldView（A01 / A04 / K01）
        ↓
QR 规范 + 对齐计划                        ← 每模版生成，不是人工配
```

- **业务字段字典**：字段 = 业务概念，与模版无关。A01/A04/K01 同属 `liaj-diagnosis`，共用同一份字典。
- **模版视图**：只声明两件事 —— 哪些字段在本模版出现、哪些属性在本模版被覆写。是**数据**，不是第二份字段表。
- **对齐计划**：由 §6 的流程自动生成 + 人工审核，不手工维护。

关键：**新增模版不再新增字段**。模版 = 一个 templateId + 一份 QR 规范 + 一份自动生成的对齐计划 + 少量覆写。

### 12.2 能共用 / 不能共用

| 能共用（docType 级，配一次） | 不能共用（模版级，必须各自表达） |
| --- | --- |
| 字段 ID、字段名、字段类型、分组 | QR token index（跨模版完全不同） |
| プロンプト 的默认值 | 字段在该模版中的位置与顺序 |
| 正解サンプル 的默认值 | 值的**形态变体**（A01 生年月日是西历 `1960`，K01 是 `昭和 / 42`） |
| 処理ルール（绝大多数） | 正常条件阈值（形态不同 → 量纲不同） |
| 值域字典（可跨 docType 复用） | 模版特有的プロンプト / 正解サンプル |
| HITL / 必须 / マスク 的**默认值** | 上述三项的模版级覆写 |

一句话：**业务语义共用，位置与形态不共用。**

### 12.3 三个机制

**（a）`applicability` 适用性** —— 表达"这个模版没有这个字段"

```jsonc
{ "fieldId": "f_088", "name": "傷病名",
  "applicability": { "mode": "all", "except": ["LIAJ001-K01-202604"] } }
```

默认 `mode: "all"`（全集适用），模版按需排除。默认全集而非默认子集，是为了让新增模版不必重配一遍字段。未适用字段在该模版的 OCR 抽取、Step5 卡片、正常条件校验、必须校验中一并跳过。

**（b）`variants` 形态变体** —— 表达"同一字段在不同模版形态不同"

```jsonc
{ "fieldId": "f_006", "name": "生年月日",
  "variants": [
    { "templateId": "LIAJ045-A01-202104", "shape": "westernYear", "sample": "1960", "rules": ["半角変換（数字）"] },
    { "templateId": "LIAJ001-K01-202604",  "shape": "eraYear",     "sample": "昭和 42", "rules": ["全角変換", "スペース削除"] }
  ] }
```

变体直接决定该模版的 プロンプト、正解サンプル、処理ルール 与正常条件量纲。**这是共用字段最容易漏掉的坑**：共用一个 `生年月日` 字段没问题，共用一套阈值就会误判。

**（c）`override` 覆写** —— 表达"同一字段在不同模版策略不同"

可按模版覆写：`required`、`hitl`、`mask`、`normalRange`、`プロンプト`、`正解サンプル`、字段顺序。覆写只记差异，未覆写即继承字典默认值。

### 12.4 字段字典从哪来

不需要人工从零建：

1. 取该 docType 下已有模版的字段表做并集去重（A01 ∪ A04 ∪ K01）。
2. 同义字段名聚类（`患者氏名` / `患者名` / `氏名`）：用**类型 + 值域 + 分组**做信号，模型给合并建议，admin 确认。**同名不自动合并**——同名不同义（A01 的「手術名」指主手术，K01 的可能指术式分类）必须由人裁决。
3. 落库为字典 v1，之后只增量。

### 12.5 落地路径

| 路径 | 做法 | 适用 |
| --- | --- | --- |
| A · 派生（过渡） | 模版间字段表**继承**：A04 = 基于 A01 创建，只记增 / 删 / 改。UI 上"基于某模版创建" | 先解"不要每个模版配一遍"的痛点，改动小，现有结构即可承载 |
| B · 字典（目标态） | docType 级字段字典 + 模版视图 + 变体 | 彻底一套字段，模版只剩 QR 规范与计划 |

两条路的数据结构是兼容的——派生就是"全集的一个子集 + 覆写"，与路径 B 的视图同构。可以先做 A，后平滑升级到 B，不必一次到位。

注意：二期字段表挂在**账票类型**下（`帳票タイプ設定` Step2）。改到 docType 级是数据结构变更，需要明确 docType 与账票类型的关系（一个 docType 对应多个账票类型，还是账票类型即 docType 的实例）。这是路径 B 的前置决策，建议在动工前定稿。

### 12.6 模版最终剩下什么

| 项 | 来源 | 人工成本 |
| --- | --- | --- |
| templateId / 帐票码 | QR 规范 | 导入 |
| QR 规范（token 表 + 样张） | 帐票仕样 | 导入 |
| 字段子集 + 变体 + 覆写 | 模版视图 | 少量勾选/覆写 |
| 对齐计划 | §6 自动生成 | 审核一次 |

### 12.7 风险

| 风险 | 对策 |
| --- | --- |
| 字段字典膨胀（模版专属字段堆积） | UI 按分组折叠 + 按模版过滤视图；字典只增不删，废弃走 deprecate 标记 |
| 误共用（同名不同义） | 同名不自动合并，只由人确认；字段 ID 稳定，改名不动 ID |
| 变体爆炸（一个字段在每个模版都不同形态） | 设阈值：变体超过 3 个 → 提示该字段应拆成多个业务字段，而非继续加变体 |
| 子集标错（模版其实有该字段却标了不适用） | 用"必需字段覆盖率"兜底；Step5 出现意外空卡片可人工发现并修正视图 |
| 跨 docType 过度共用 | 字段字典严格按 docType 隔离；**只有值域字典与处理规则可跨 docType 复用** |

## 13. 是否引入大模型，与客户配置方式未定时的推进路径

### 13.1 先把一个混在一起的问题拆成两个

"QR 字段与 OCR 字段归一"实际是两件事，LLM 的必要性完全不同：

| | 子问题 A · 结构对齐 | 子问题 B · 格式归一 |
| --- | --- | --- |
| 问的是什么 | 哪个 QR 位置对应哪个 OCR 字段 | 同一字段，两侧的值形态不同，统一成哪种 |
| 数学性质 | 匹配问题（可能无解、多解） | 转换问题（有穷、可枚举） |
| 依赖客户 | 依赖（要有 OCR 字段列表才能对） | 不依赖（只要知道目标格式） |
| LLM 必要性 | 有条件有用 | **不需要** |

混在一起谈会得出错误结论。分开谈结论很清楚。

### 13.2 结论：引入，但只引入在"判断"环节，"执行"环节绝不用

| 环节 | 用 LLM | 理由 |
| --- | --- | --- |
| 值格式转换（日期、全半角、年号、去空格） | 否 | 有穷可枚举，规则更快更稳可测；用模型反而引入不确定性 |
| 拼接、`$`/`^` 切分、`!s` 还原 | 否 | 纯字符串操作 |
| flag group 识别（哪些位是一组） | 否 | 多样张统计即可（恒为恰一个 1） |
| 管理字段剔除（头部系统区） | 否 | 结构位置确定性 |
| 规则**选择**（这个字段该用哪条 処理ルール） | 可 | 从 15 条里做选择题；结果缓存为计划 |
| flag label 配对（位 ↔ 选项名） | 可 | 有字段名时不必用；无字段名时作兜底 |
| QR 字段名 → 业务字段名 归一 | 可 | 剥序号前缀是规则；跨名同义合并才需模型 |
| QR 字段 ↔ OCR 字段 对齐 | 可（可降级） | 有字段名时规则+模糊匹配够用；无字段名才靠模型 |
| 业务性剔除（无对应、恒常量、内码） | 可 | 靠值域 + 样本，模型只做裁决 |

**一句话：模型负责"选哪个"，代码负责"怎么转"。**

这条原则在当前约束下更有价值 —— 它允许把确定性的那部分先做完，模型部分延后接入，两者之间是一份数据契约（对齐计划），不是耦合代码。

### 13.3 格式归一以谁为准

必须明确，否则"格式统一"无法落地。两种选法：

| 选法 | 后果 |
| --- | --- |
| 以 OCR 侧为准 | OCR 自身格式可能随模型/置信度漂移，QR 跟着漂移；量纲不稳定 |
| **以标准格式为准（建议）** | 两侧都往标准格式转；格式与数据来源解耦 |

建议后者：在字段定义里写死标准格式（如日期 `YYYY/MM/DD`、数字半角无千分位、姓名全角、都道府県 无空格），QR 与 OCR 各自向它转换。这样处理规则、正常条件阈值、下游消费都对着同一个量纲，且与"后处理规则挂在业务字段上、与数据来源无关"（§8.1）一致。

### 13.4 对比两侧字段列表做归一的机制

核心：**不要直接比字段名，比三类信号，然后按置信度分流。**

```
信号 1 · 名字      字符重合 / 编辑距离 / 去序号前缀后的 token 重合
信号 2 · 值域      两侧样本集合的重合度（完全一致 > 包含 > 不相容）
信号 3 · 位置      分段位置、字段分组、在各自列表中的相对顺序
        ↓
候选生成 + 打分（确定性代码，不调模型）
        ↓
高分（唯一候选 且 值域相容）→ 直接落计划，不调模型
中分（多候选 或 值域部分相容）→ 交模型做选择题
低分（无候选 或 值域不相容）→ drop 或 unresolved
```

要点：

- **名字是加速器，不是必要条件。** 有名字时信号 1 直接命中，模型几乎不用；没名字时退到信号 2 + 3，模型承担更多。系统必须在名字缺失时**降级而不是崩溃**。
- **值域是最强信号。** `継続` 两侧完全一致比任何名字相似度都可靠；`2026` 与 `2026/05/18` 是包含关系，可直接判为同一字段的不同形态。
- **模型只吃中分段。** 高分段与低分段都是确定性判定，模型的实际负载远小于"全量对齐"。这个比例必须用 LIAJ 三个模版的真实数据量化，作为成本评估依据。
- **跨模版复用。** 同 docType 下，模版 A 的配对结果作为模版 B 的候选先验（A01/A04 布局共享约 24%），第二个模版的模型调用量显著小于第一个。模版越多，边际成本越低。

### 13.5 客户配置方式未定 → 现在能推进的四件事

关键认识：**QR 侧归一的大部分工作不依赖 OCR 字段表，现在就能做。** 把依赖客户决策的部分压到最小。

| # | 可先做 | 依赖客户 |
| --- | --- | --- |
| 1 | QR 侧内部归一：字段名剥序号前缀、值格式归一（日期拼装、年号→西历、全半角、`!s`）、flag group 归并、管理字段剔除 | 不依赖 |
| 2 | 用 1 的结果**反向产出 OCR 字段表草案**，作为给客户的提案 | 不依赖（反而帮客户做决策） |
| 3 | 三信号候选生成 + 阈值分流的框架，高分段先跑通，模型段留接口 | 不依赖 |
| 4 | 用 LIAJ A01/A04/K01 做验证集，量化高/中/低分段占比与归一准确率 | 不依赖 |

第 2 项值得单独强调：**客户不知道怎么配字段，是因为他们手上没有一个候选清单。** LIAJ 診断書的 QR 里本来就携带完整的业务字段集合，QR 侧归一完成后天然就是一份字段表草案。把它整理出来给客户看，比追问"你们打算怎么配"更容易推进。

等客户明确的部分：字段表是 docType 级还是模版级（决定对齐计划的作用域与继承方式）、哪些字段必填、HITL 策略。**这些只影响对齐层的作用域，不影响算法本身** —— 客户选哪种，第 1～4 项都不浪费。

### 13.6 与 §12 的关系

§12 讨论"能不能共用字段"，本质是**对齐层的作用域**问题；本节讨论"要不要用模型"，本质是**对齐层内部的分工**问题。两者正交，可以并行决策：作用域未定时，先按"作用域可参数化"的方式实现，客户决策落地后只改一个配置项。
